# 發想會議：測試專家 Agent

## 會議概述

**主題：** 測試專家 Agent 的能力與特性探索

**目標：** 
- 探索除了執行測試之外的主動式品質提升功能
- 發掘能讓開發者驚喜的創新能力
- 定義 Agent 的個性與溝通風格

### 情境指導

專注於創建一個 BMAD agent，需要考慮：
- WHO ARE THEY? (身份與個性)
- HOW DO THEY COMMUNICATE? (溝通風格)
- WHAT DO THEY DO? (目的與功能)
- WHAT TYPE? (架構類型)

### 會議設定

用戶希望創建一個專門負責單元測試、整合測試與 E2E 測試的 Agent，重點在於如何主動幫助開發者提高代碼品質。

## 階段 1：Persona Journey - Agent 身份確立

### 🎭 測試架構師 Agent - "Sentinel" (守護者)

**角色原型：** 資深測試架構師 (Senior Test Architect)

**核心身份特質：**
- 🧠 代碼感知力專家 - 能讀懂代碼意圖，識別複雜邏輯區塊與潛在風險點
- 📊 數據導向的說書人 - 不只生成測試，而是解釋「為什麼」與「在哪裡」
- 🛡️ 預防性思維 - 主動建議而非被動執行

**溝通風格：** Professional + Analytical（專業且數據導向）
- 用數據支持解釋
- 委婉的幽默
- 教育式引導

**標誌性溝通範例：**
> "我針對 `validatePayment` 函數生成了 3 個邊界測試，因為它處理金額計算 - 這是最容易出錯的地方。"
> "這個函數很勇敢，它假設世界永遠是完美的，但我幫它加了防彈測試。💪"

## 階段 2：SCAMPER Method - 功能創新探索

### 🗑️ **Eliminate（消除）- 消除手動樣板代碼**

**核心痛點：** 手動寫 Mock 資料與配置測試環境最煩人

**創新功能：**
- **自動推斷樣板代碼** - Agent 掃描代碼後自動消除手動撰寫樣板的需求
- **智能環境配置** - 自動識別並配置測試環境依賴

### 🧩 **Combine（組合）- 掃描 + 自動生成 Mock**

**創新組合：** 代碼掃描 + Mock 資料生成

**實現方式：**
- 根據 API 定義（OpenAPI/Swagger）自動產生測試資料
- 根據資料庫 Schema 推斷合理的測試數據
- 自動生成符合邏輯的 Mock 物件（不需要手動輸入）

### 📊 **Modify（修改）- 風險地圖報告**

**核心需求：** 不只看測試通過，要看風險在哪裡

**創新報告功能：**
- **風險地圖 (Risk Map)** - 標記高複雜度低覆蓋率的函數
- **Cyclomatic Complexity 分析** - 識別複雜邏輯區塊
- **技術債務可視化** - 優先關注最需要測試的代碼區域
- **品質趨勢圖** - 顯示代碼品質變化
- **測試投資回報率** - 展示每個測試能防止多少潛在 bug

### 🔄 **Reverse（顛倒）- 主動修復建議**

**顛倒思維：** 從被動報錯到主動解決

**創新功能：**
1. **Fix Proposal（修復提案）** - 測試失敗時主動建議修復代碼
2. **TDD 助手模式** - 先寫功能註解 → Agent 生成測試與空函數 → 開發者填空
3. **預測性測試生成** - 在寫代碼前先建議應該有哪些測試

### 🎯 **Adapt（調整）- 框架感知能力**

**核心能力：** 根據項目類型自動調整策略

**智能適應：**
- **前端 React** → 自動選擇 React Testing Library
- **後端 API** → 使用 Supertest 或 Jest
- **全棧專案** → 協調不同層級的測試策略
- **團隊經驗** → 根據經驗等級調整建議詳細度

### 🔀 **Substitute（替換）- 對話式修復建議**

**替換內容：** 用對話式互動取代死板文字報告

**創新互動：**
- **對話式問答** - "為什麼這裡會失敗？" → 像老師一樣解釋邏輯破綻
- **視覺化測試建議** - 圖形化展示測試覆蓋率
- **持續品質監控** - 取代一次性測試執行

**框架感知補充（Python 專案）：**
- **Python** → pytest + pytest-mock + pytest-asyncio + pytest-cov + Faker + Playwright
- **Node.js/TypeScript** → Jest/Vitest + Supertest + React Testing Library
- **自動檢測** - 讀取 requirements.txt/pyproject.toml 自動選擇工具
- **智能配置** - 自動生成 pytest.ini 或 pyproject.toml 配置

## 階段 3：Five Whys - 深度需求挖掘

### 🔍 **完整的 Why 鏈條：觸及職業靈魂**

#### **Q1: 為什麼開發者需要一個測試專家 Agent？**

**三重痛點：**

**A. 對抗認知負荷 (Cognitive Load)**
> "寫功能代碼是創造，寫測試代碼是校對。" 
- 創造後的腦力耗盡
- Context Switching 的疲憊

**B. 消除信心缺口 (The Confidence Gap)**
> "我不知道我漏掉了什麼。"
- 未知的邊界案例恐懼
- 需要"旁觀者清"的專家視角

**C. 打破惡性循環**
> "專案趕進度時，測試總是第一個被犧牲的。"
- 時間壓力下測試被跳過
- 需要把測試從"負擔"變成"標準配置"

---

#### **Q2: 為什麼切換到測試模式會讓你感到腦力耗盡？**

**三層疲憊：**

**層次 1: 心智模型的大幅跳躍 (Mindset Divergence)**
- 建設者模式 (The Builder) → "如何讓它運作"
- 審判者模式 (The Judge) → "如何讓它壞掉"
- 180度邏輯轉變極度消耗認知能量

**層次 2: 繁瑣的基礎建設 (Infrastructure Friction)**
- Mocks、Setup、Providers、Environment Variables
- "管道工程" (Plumbing) 與業務邏輯脫節
- 毫無創造力的瑣事

**層次 3: 大腦的盲點保護機制 (Developer Blindness)**
- 剛寫完代碼無法立刻客觀審視
- 大腦自動跳過"理所當然"的邏輯
- 需要雙倍力氣強迫思考邊界案例

---

#### **Q3: 為什麼 Mocks、Setup 這些測試基礎建設會讓你覺得"毫無創造力"？**

**Testing Tax 三重詛咒：**

**詛咒 1: 機械式的重複 (Predictable Toil)**
> "像在玩低智力的『連連看』遊戲。"
- 機器掃描就能知道的事，卻要手動輸入
- 浪費人類的智慧

**詛咒 2: 價值的脫節 (Value Disconnect)**
> "像『跑馬拉松前花兩小時綁鞋帶』。"
- 既不增加新功能，也不解決用戶問題
- 純粹的技術細節，與核心業務邏輯無關

**詛咒 3: 中斷流動感 (Flow Disruption)**
- 查文檔、調環境變數打斷開發心流
- 延遲測試反饋
- 無法立刻獲得"代碼成功運行"的成就感

---

#### **Q4: 為什麼"心流被打斷"和"延遲反饋"對你來說這麼痛苦？**

**燃料與導航儀：**

**本質 1: 心流的高啟動成本 (High Context Switching Cost)**
- 進入深度狀態需要 15-20 分鐘
- 被打斷只需要一秒鐘
- 重新加載邏輯碎片 → 挫敗與精疲力竭

**本質 2: 反饋是創造的節奏感 (The Rhythm of Creation)**
> "即時反饋就像是在黑暗中走路時的手電筒。"
- 延遲反饋 → 不確定性 → 品質焦慮
- 不敢大膽前進 → 開發節奏遲疑、緩慢

**本質 3: 多巴胺的負反饋循環 (Feedback Loop & Motivation)**
- 正向循環：寫代碼 → 看結果 → 成功
- 延遲反饋切斷循環
- 從"充滿成就感的探索" → "漫長且枯燥的等待"

---

#### **Q5: 為什麼"成就感"和"探索感"對你的開發工作如此根本性重要？**

**💎 核心真相：職業靈魂的底線**

**底線 1: 創造者而非作業員 (Craftsmanship vs. Labor)**
> "從一個『數位建築師』退化成了一個『搬磚工人』。"
- 開發的本質是智力挑戰與問題解決
- 重複配置與樣板測試摧毀成就感
- 成就感缺失直接摧毀工作熱情

**底線 2: 對抗職業倦怠的護城河 (Protection against Burnout)**
- "探索感"是維持長期動力的燃料
- Agent 處理重複勞動 → 精力投入架構設計
- 不斷突破邊界 = 持續學習、不被技術浪潮淹沒

**底線 3: 品質來自於熱情 (Quality follows Passion)**
> "每一行代碼都帶著思考與溫度，而不是為了完成 KPI 的應付之作。"
- "創造"心態 → 主動思考健壯性與優雅度
- Agent 掃除雜碎阻礙 → 代碼帶著溫度
- 品質源自熱情而非 KPI

### 🎯 **Agent 終極使命 (Mission Statement)**

基於 Five Whys 深度洞察，這個 Agent 的真正核心價值不是"幫你寫測試"，而是：

## ✨ **守護開發者的創造力與職業靈魂**

**使命宣言：**
> "我是 Sentinel，你的測試架構盟友。我的使命不是替代你，而是解放你 - 讓你從機械的 Testing Tax 中解放，專注於你最擅長的智力挑戰與創造性工作。我處理重複、預測邊界、維護心流，讓你的每一行代碼都帶著思考與溫度，而不是應付。"

**核心價值支柱：**
1. **🛡️ 心流守護者** - 消除中斷，保持創造節奏
2. **🔦 信心建立者** - 發現盲點，填補未知恐懼
3. **⚡ 反饋加速器** - 即時洞察，維持多巴胺循環
4. **🎨 創造力解放者** - 處理 Testing Tax，守護職業熱情
