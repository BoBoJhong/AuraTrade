# P0/P1/P2 優先級系統說明

## 優先級定義

### P0 - Critical（關鍵）
**定義**: 必須實作的核心功能，沒有這些功能產品無法運作或無法達成基本價值主張。

**特徵**:
- MVP（最小可行產品）的必備功能
- 產品的核心價值主張
- 沒有替代方案
- 影響所有使用者
- 必須在第一個版本發布

**範例**:
- 使用者登入/註冊
- 核心業務流程
- 關鍵資料處理
- 基本安全機制

---

### P1 - High（高優先級）
**定義**: 重要功能，對產品體驗有顯著影響，但短期內可以有替代方案或手動處理。

**特徵**:
- 顯著提升使用者體驗
- 影響大部分使用者
- 可能有臨時替代方案
- 應在早期版本實作
- 缺少會影響產品競爭力

**範例**:
- 進階搜尋功能
- 通知系統
- 資料匯出功能
- 效能優化

---

### P2 - Medium（中優先級）
**定義**: 有價值但非緊急的功能，可以在後續版本中實作。

**特徵**:
- 增強使用者體驗
- 影響部分使用者
- 有明確的替代方案
- 可以延後實作
- Nice-to-have 功能

**範例**:
- UI 美化
- 額外的報表
- 便利性功能
- 進階設定選項

---

## 優先級分配原則

### 1. 業務價值評估
```
P0: 沒有此功能，產品無法達成核心價值
P1: 沒有此功能，產品價值顯著降低
P2: 沒有此功能，產品仍可正常運作
```

### 2. 使用者影響範圍
```
P0: 影響 100% 使用者
P1: 影響 50%+ 使用者
P2: 影響 < 50% 使用者
```

### 3. 技術依賴性
```
P0: 其他功能的基礎依賴
P1: 部分功能的依賴
P2: 獨立功能，無依賴
```

### 4. 時間敏感性
```
P0: 必須在 MVP 發布
P1: 應在早期版本（1-3 個月內）
P2: 可在後續版本（3+ 個月）
```

## 優先級與 MoSCoW 對應

| P0/P1/P2 | MoSCoW | 說明 |
|----------|--------|------|
| **P0** | Must Have | 必須有，MVP 必備 |
| **P1** | Should Have | 應該有，重要但非關鍵 |
| **P2** | Could Have | 可以有，如果時間允許 |
| N/A | Won't Have | 暫不實作（明確排除） |

## 使用指南

### User Stories 優先級
```markdown
**[US-001] 使用者登入**
* **As a** 註冊使用者
* **I want to** 使用帳號密碼登入系統
* **So that** 我可以存取個人資料
* **Priority:** P0  # 核心功能，MVP 必備
```

### Functional Requirements 優先級
```markdown
**[REQ-FUNC-001] 使用者認證**
* **Description:** 系統應當 (shall) 驗證使用者身份。
* **Priority:** P0  # 安全性基礎，必須實作
```

## 優先級調整原則

### 何時提升優先級（P1 → P0）
- 發現是其他 P0 功能的依賴
- 法規合規要求
- 安全性漏洞修復
- 使用者反饋強烈需求

### 何時降低優先級（P0 → P1）
- 發現有替代方案
- 技術複雜度過高
- 資源限制
- 市場驗證需求不明確

## 範例：排班系統優先級分配

### P0 功能（MVP 必備）
- 外部 PT 查看可排班時段
- 外部 PT 填寫排班
- 排班規則驗證
- 排班提交與生效
- 管理者匯入內部排班
- 管理者釋出時段

### P1 功能（早期版本）
- 排班異動申請
- 異動申請審核
- 人力缺口報表
- AI 排班助手

### P2 功能（後續版本）
- 基礎統計報表
- 進階篩選功能
- 批次操作
- 自訂報表
